# meelTe — Design & Color Reference (Next.js Marketing Website)

This document describes the design tokens and color system the **meelTe Next.js marketing website** (`nextjs-website`) uses today. It documents the existing implementation only; nothing in the site was changed to produce it. Recommendations are kept apart, in [section 9](#9-inconsistencies-and-recommendations).

The Flutter app (`meelTe_user`, `com.meelTe.classico`) and the admin panel are separate codebases and are **not** covered here. Where the app has its own token class, this site has a Tailwind v4 `@theme` block — the values overlap, the mechanisms do not.

**Scope of the analysis (2026-10-29)**

- All **69** `.js` / `.jsx` files under `src/` were scanned for Tailwind color utilities, arbitrary values (`bg-[#…]`), raw palette utilities (`bg-emerald-50`), plain hex literals, and `var(--color-*)` reads.
- All **181** lines of [`src/app/globals.css`](../src/app/globals.css) were read by hand: the `@theme` block, the `:root`/`html`/`body` base layer, the Radix accordion keyframes, the `prefers-reduced-motion` block, and the sonner toast token block.
- The JS palette mirror, the viewport/theme-color config, the PWA manifest, and the generated OpenGraph card were checked, because they consume brand colors outside CSS.
- Not analyzed:
  - colors baked into raster and SVG assets in `public/` (`Logo.svg`, `Filled_Logo.png`, `only_meelTe.png`, `icon.png`, `apple-icon.png`)
  - the exact output of `@vercel/og` beyond the `BRAND_COLORS` values it is handed
  - browser-injected styling for native form controls, scrollbars, and autofill

## 1. Overview

The site has a **single light theme** built around a **purple brand color, `#6D3BB3`**, on a very light, violet-tinted canvas (`#F8F5FF`) with pure white cards (`#FFFFFF`). Body text is a near-black blue-grey (`#1F1F28`), secondary text a cooler grey (`#4B5563`), and de-emphasized meta text a light grey (`#9CA3AF`).

Accents come from three places:

- an **amber** accent (`#F59E0B`) reserved for the Play Store / download path and the merchant conversion blocks
- **status colors** (green, orange, red, blue) used almost exclusively for form validation and toasts
- **purple gradients** (`primary` → `primary-hover` → `primary-royal`, or `primary` → `indigo-500` → `violet-500`) on hero headlines, hero mock panels, and every bottom-of-page CTA

The visual character is soft and community-oriented:

- rounded surfaces (`rounded-2xl`) with **purple-tinted** shadows rather than neutral grey ones
- a strong purple used sparingly: primary buttons, links, active nav state, icon tiles, focus rings
- a lot of very light violet: `surface-muted` chips behind purple icons, `primary/10` borders, `canvas` page background

Unlike the Flutter app, the website **does** have a real token layer: 24 color tokens in one `@theme` block, and the great majority of UI color comes through them. It is not airtight, though. **115 raw palette utilities** across 20 files (mostly `emerald`, `amber`, `indigo`, `violet`, `purple`, `fuchsia`, `blue`, `red`) sit outside the token set, there are 7 arbitrary hex values, and the JS palette mirror in `app-constants.js` has **drifted from the CSS** in two places (see [9.4](#94-the-js-palette-mirror-has-drifted-from-the-css)).

Two of these files matter:

- **`globals.css` is the source of truth for anything rendered by CSS.** Every `--color-*` token becomes a set of Tailwind utilities.
- **`app-constants.js` is the source of truth for anything rendered outside CSS** — the PWA manifest, the browser `theme-color`, and the generated OG image, which `@vercel/og` renders from inline styles rather than from the stylesheet.

There is **no** `tailwind.config.js`, **no** `postcss.config.js`, and **no** theme provider. Tailwind v4 is configured entirely in CSS; [`next.config.mjs`](../next.config.mjs) only wires `@tailwindcss/turbopack` to `*.css`.

### 2.2 How the token layer works

`src/app/globals.css` opens with `@import "tailwindcss";` followed by a single `@theme` block. In Tailwind v4 this is the whole configuration:

- every `--color-<name>` generates the matching `bg-`, `text-`, `border-`, `from-`, `via-`, `to-`, `ring-`, `fill-`, `stroke-`, `divide-`, `outline-`, `shadow-`, `placeholder-`, `caret-` and `accent-` utilities
- every `--shadow-<name>` generates `shadow-<name>`
- every `--radius-<name>` generates `rounded-<name>`
- every `--font-<name>` generates `font-<name>`
- opacity modifiers work on tokens: **336** utilities use one (`border-border/80`, `bg-primary/20`, `text-foreground/[0.03]`, …)

No component writes `var(--color-*)` directly; **zero** `.js`/`.jsx` files read a CSS custom property by name. Components read tokens exclusively through generated utilities, which is why changing a token value in `globals.css` updates every use site.

### 2.3 How colors are consumed (measured across `src/`)

| Mechanism | References | Where |
|---|---:|---|
| Colour token utility classes (`bg-primary`, `text-foreground-secondary`, …) | **1,135** | every page component |
| of which opacity-modified (`bg-primary/20`, `border-border/80`, …) | 336 | 20 files |
| Shadow tokens (`shadow-soft`, `shadow-card`) | 75 | 24 + 12 files |
| Raw Tailwind palette utilities (`bg-emerald-50`, `from-indigo-500`, …) | **115** | 20 files |
| Plain hex literals in JS/JSX | 27 (15 distinct values) | 9 component files, the `BRAND_COLORS` mirror, and 1 code comment |
| Arbitrary-value utilities (`bg-[#f7f3ff]`, `to-[#4A247A]`, …) | 7 | 7 files |
| `var(--color-*)` reads in components | **0** | — |
| `focus-visible:ring-*` (brand-ringed focus) | 102 | 16 files |

**Token utilities outnumber palette utilities roughly 10:1.** The color system is real and mostly enforced; the leaks are concentrated in the emerald "verified / 0% commission" badges and the hero gradient accents, both detailed in [section 9](#9-inconsistencies-and-recommendations).

Unused at the utility level (defined, never referenced as a Tailwind class): `--color-primary-light`, `--color-border-subtle`, `--color-border-focus`, `--color-success`, `--color-warning`, `--color-info`, `--shadow-card-hover`, `--radius-card`, `--radius-pill`, `--font-sans`, `--font-mono`. Most of these are still used — through `var()` inside `globals.css` itself (the sonner block, the body rule) or via the JS mirror — so they are **not** dead values, only unused as utilities. See [9.6](#96-tokens-that-are-never-used-as-utilities).

## 6. Theme Modes

- **Light only. There is no dark mode.** This is a factual property of the repository, not a preference:
  - `html { color-scheme: light; }` ([`globals.css:61`](../src/app/globals.css)).
  - **No `.dark` selector exists anywhere** in `src/`. There is no `@custom-variant dark`, no `.dark { … }` block, and no dark token overrides.
  - No `next-themes`, no `ThemeProvider`, no `useTheme`, and **no `prefers-color-scheme` query** in the codebase.
  - `viewport.colorScheme` is the literal string `"light"` ([`metadata.js:149`](../src/lib/seo/metadata.js)).
  - The single `Toaster` is pinned: `theme="light"` ([`layout.js`](../src/app/layout.js)).
  - No theme toggle component exists.

  The site therefore looks identical when the operating system is in dark mode. Any future dark mode needs new `.dark` token overrides **and** replacements for the raw palette utilities and hex literals in [3.4](#34-colors-used-outside-the-token-set), because those cannot switch.

- **`:root` holds two unused declarations.** `--background: #F8F5FF` and `--foreground: #1F1F28` ([`globals.css:54-57`](../src/app/globals.css)) are not Tailwind tokens and nothing reads them; `body` uses `var(--color-canvas)` and `var(--color-foreground)` instead. They look like a leftover from an earlier token-naming scheme.

- **Motion preferences** are honoured globally, not per component: `globals.css:138-157` forces `animation-duration`, `transition-duration` and `scroll-behavior` to their minimums under `prefers-reduced-motion: reduce` (and zeroes the `.faq-panel` `transition-delay`). This covers the FAQ accordion, the `animate-pulse` live dots, and hover transitions without each component opting in.

- **Browser and PWA surfaces** are brand-aligned, unlike the Flutter app's default `#0175C2`: `theme-color` is `#6D3BB3` and the manifest's `background_color` is `#F8F5FF`.

## 7. Color Usage Guidelines

These conventions already exist in the code. They describe what the source states or consistently does; they are not new rules.

1. **Reach for a token first.** Every structural color has one. `bg-canvas` for pages, `bg-surface` for cards, `text-foreground` / `text-foreground-secondary` / `text-foreground-muted` for the three text levels, `border-border` for outlines.
2. **Primary purple `#6D3BB3`** is for primary actions, links, active navigation, icon tiles, and focus rings — not for large paragraph text or full-page fills.
3. **Amber `#F59E0B` pairs with `accent-foreground` (`#1F1F28`), never with white.** The dark text is not a stylistic choice; white on amber fails contrast (see [section 8](#8-accessibility-notes)).
4. **Opacity modifiers are the shading system.** Tints are produced with `primary/10`, `border/80`, `foreground/[0.03]` rather than by adding new hex values — 336 utilities do this.
5. **Shadows are purple, not grey.** `shadow-soft` for resting cards, `shadow-card` for hover and CTA blocks. Do not introduce a neutral `rgba(0,0,0,…)` shadow.
6. **Focus is always `ring-2 ring-primary/40 ring-offset-2`** on interactive controls (the dominant pattern across the site). `globals.css` also ships a `.focus-ring` class doing the equivalent with `outline`, but **no component uses it** — the utility form is the de facto standard. `ring-primary/40` composites to ≈1.96:1 on light surfaces, below the 3:1 focus-indicator requirement in WCAG 1.4.11, so the shared `Button` primitive and the `/about` and `/contact` rebuilds use `ring-primary/70` (≈3.6:1) instead. The rest of the site still uses `/40`.
7. **Validation uses `error` only.** Invalid fields get `border-error`; messages and required-field asterisks get `text-error` (the `/contact` rebuild removed the last raw `text-red-500`).
8. **Feedback goes through the toast contract.** Components import `notifySuccess` / `notifyError` / `notifyInfo` from `src/lib/toast-feedback.js`; the colors are set once in the sonner block, never per call site.
9. **Icons are decorative or accent-colored, never load-bearing.** Every icon-only control carries an `aria-label`, so color is never the only channel for meaning.

## 8. Accessibility Notes

Contrast ratios were **calculated** with the WCAG 2.x relative-luminance formula from the values in `globals.css` and the components, for opaque color pairs. They were **not** measured in a browser, and they ignore alpha blending (336 utilities use it), gradients behind text, font rendering, and the purple-tinted shadows.

WCAG AA thresholds:

- normal text needs **4.5:1**
- large text (≥ 18pt, or ≥ 14pt bold) needs **3:1**
- non-text UI parts (borders, icons, focus indicators) need **3:1**

## 9. Inconsistencies and Recommendations

### 9.1 Two competing headline gradients

The brand's most visible type treatment — the gradient on every hero `h1` — does not use brand tokens for two of its three stops:

- **Token-based (correct):** `from-primary via-primary-hover to-primary-royal` → `#6D3BB3 → #5B2E91 → #6B2C70`. Used on the three bottom CTAs, `for-merchants-hero.jsx`'s floating card, and — since the Oct 2026 rebuilds — the `h1` of `/careers` (`careers-hero.jsx`), `/about` (`about-hero.jsx`) and `/contact` (`contact-hero.jsx`). The `/about` hero previously ended in `to-accent`, which put `#F59E0B` under large text at 2.15:1 (§9.8).
- **Raw palette (dominant):** `from-primary via-indigo-500 to-violet-500` → `#6D3BB3 → #6366F1 → #8B5CF6`. Used on the `h1` of `/` (`hero-section.jsx:334`), `/discover` (`discover-hero.jsx:126`), `/for-merchants` (`for-merchants-hero.jsx:200`), and `/how-it-works` (`how-it-works-hero.jsx:349`).

### 9.6 Tokens that are never used as utilities

Defined in `@theme` but never referenced as a Tailwind class:

- **Still used through `var()` inside `globals.css`:** `success`, `warning`, `info` (sonner status text), `border-focus` (sonner focus ring), `font-sans` (the `body` rule), `primary-foreground` is *not* in this group — it has one real use.
- **Genuinely unused:** `primary-light` (no longer rendered anywhere after the runtime OG card was removed), `border-subtle`, `shadow-card-hover`, `radius-card`, `radius-pill`, `font-mono` (no `font-mono` class in components).

`radius-card` and `radius-pill` are the clearest waste: components write `rounded-2xl` and `rounded-full` directly, so changing `--radius-card` would change nothing. Likewise `hover:shadow-card` is used 21 times while `shadow-card-hover` — the shadow written for exactly that purpose — is used zero times.

### 9.7 Declared-but-dead declarations in `globals.css`

- `:root { --background: #F8F5FF; --foreground: #1F1F28; }` — nothing reads them. `body` uses `var(--color-canvas)` / `var(--color-foreground)`.
- `.focus-ring` (`.focus-ring:focus-visible { outline: 2px solid var(--color-primary) }`) — **zero** usages. All 102 focus indicators are `focus-visible:ring-2 focus-visible:ring-primary/40`. The class and the utility convention are two different implementations of the same intent, and the class lost.
- `--color-primary-dark` is an exact duplicate of `--color-primary-hover`; one use each.

### 9.8 Amber is doing two jobs

`accent` is used both as a **fill** (buttons, badges, icon tiles — 28 uses) and, in a few places, as a **text or icon color**, where it measures 2.15:1 on white. `accent-foreground` exists and is used correctly 8 times; the failures are places where amber itself became the foreground.

### 9.9 Recommendations (not applied)

1. **Pick one headline gradient and token it.** The six heroes should share one definition. The cheapest fix is a `--color-primary-accent` token for the indigo/violet stop (or reuse `primary-light` `#7A45C4`) so the gradient stops being `indigo-500`/`violet-500`/`fuchsia-400`.
2. **Token the semantic-pass colors.** Add `--color-positive-*` (or map the existing `success`) and replace the 60-plus emerald utilities with it. Add `--color-category-*` and `--color-persona-*` if the five category and three persona colors are meant to be brand-stable.
3. **Reconcile the JS mirror with the CSS.** Either fix `BRAND_COLORS.textSecondary` → `#4B5563` and `accentHover` → `#D97706` (one-line each), or delete the duplication by reading the values from a single shared module. The current split guarantees the OG card and the HTML will keep diverging.
4. **Fix the three genuine token bypasses:** `to-[#4A247A]` ×2 → `to-primary-active`, `text-[#4B5563]` → `text-foreground-secondary`.
5. **Delete the dead weight:** the `:root` `--background`/`--foreground` pair, the unused `.focus-ring` class (or adopt it and drop 102 repeated ring utilities), `--color-primary-dark`, `--radius-card`, `--radius-pill`, `--shadow-card-hover`, `--color-border-subtle`. Each is either a duplicate or a constant nothing reads.
6. **Accessibility:**
   - stop using `foreground-muted` (`#9CA3AF`) for anything that must be read — it is 2.23–2.54:1 across all three light surfaces; reserve it for decorative seconds and non-essential micro-copy
   - darken the warning toast text (or fill) — `#ED6C02` on `#FFF8EC` is 2.95:1
   - keep amber strictly as a fill with `accent-foreground` on top; never as text on white
   - consider a darker default border for form fields specifically, since `border-border` is 1.18:1 and fails WCAG 1.4.11 for the field boundary (cards are fine — their shadow and fill do the work)
   - when dark mode is eventually built, replace the raw palette and hex literals first, because `.dark` overrides cannot reach them
7. **Document that dark mode does not exist.** `AGENTS.md` previously described "dark mode via `.dark`" and listed a `portfolio-theme.md` that is not in this repository. Both were corrected while writing this document; `project-context.md` §5 now states light-only explicitly.
